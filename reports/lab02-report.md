## 3. Описание выполненных действий

### 3.1. Создание долгоживущих веток
Репозиторий был создан на GitHub. Начальный коммит сделан в ветке main. Затем от main создана ветка develop.

main — стабильная ветка, в которую попадают только релизы.
develop — интеграционная ветка для разработки следующей версии.

### 3.2. Разработка feature-веток
Созданы две feature-ветки от develop:

feature/multiply-divide

- добавлена функция multiply;

- добавлена функция divide с проверкой деления на ноль;

- обновлён main.py для использования новых функций.

feature/power-modulo

- добавлена функция power;

- добавлена функция modulo;

- обновлён main.py, при этом версия приложения была изменена на v0.3.0, что намеренно создало конфликт с первой веткой.

### 3.3. Разрешение конфликта
Причина: в feature/multiply-divide версия была v0.2.0, а в feature/power-modulo — v0.3.0. Также различался набор вызываемых функций.

Git пометил конфликт маркерами:

- <<<<<<< HEAD — вариант из текущей ветки develop;

- ======= — разделитель;

- >>>>>>> feature/power-modulo — вариант из сливаемой ветки.

Конфликт разрешён вручную: оставлена версия v0.3.0, объединены вызовы всех функций — add, subtract, multiply, divide, power, modulo. Маркеры конфликта удалены. После этого выполнен git add src/main.py и завершён merge-коммит.

### 3.4. Интерактивный rebase
Во временной ветке temp/rebase-demo сделаны три мелких коммита: wip, fix typo, update.
С помощью git rebase -i HEAD~3 они объединены в один коммит:

docs: add changelog with v0.3.0 release notes

- Added power and modulo functions
- Fixed division by zero handling

Это позволило сделать историю чище.

### 3.5. Создание релиза
От develop создана ветка release/0.3.0.

В ней:

- обновлена версия в README.md до v0.3.0;

- создан CHANGELOG.md с описанием изменений;

- изменения закоммичены.

Далее:

- release/0.3.0 слита в main;

- создан аннотированный тег v0.3.0;

- main и тег запушены на GitHub;

- release/0.3.0 слита обратно в develop.

Это нужно, чтобы релиз попал в продакшен и чтобы изменения из release не потерялись для следующей разработки.

### 3.6. Hotfix
Сценарий: в продакшене обнаружена ошибка — divide не обрабатывает деление на ноль для чисел с плавающей точкой.

От main создана ветка hotfix/0.3.1-divide-check.

В ней:

- исправлена функция divide: добавлена проверка if b == 0 or b == 0.0;

- обновлена версия в README.md до v0.3.1.

Далее:

- hotfix слит в main;

- создан аннотированный тег v0.3.1;

- main и тег запушены на GitHub;

- hotfix слит обратно в develop;

- hotfix-ветка удалена локально и на GitHub.

В ходе работы была практически освоена модель GitFlow. Стало понятно, зачем нужны долгоживущие ветки main и develop: main хранит стабильные релизы, а develop — интеграцию новых функций. ## 5. Ответы на контрольные вопросы

1. Зачем нужны две долгоживущие ветки (`main` и `develop`) в GitFlow? Почему нельзя работать только в `main`?

main хранит только продакшен-релизы. develop — интеграционная ветка для следующей версии. Если работать только в main, то незавершённые функции попадут в продакшен, будет сложно стабилизировать релизы и параллельно вести разработку.

2. В чём разница между `git merge` и `git merge --no-ff`? Когда какой использовать?

git merge может выполнить fast-forward: просто передвинуть указатель, если ветка не diverged. git merge --no-ff всегда создаёт merge-коммит. Для feature/release/hotfix лучше --no-ff, чтобы в истории было видно отдельную ветку.

3. Что означают маркеры `<<<<<<<`, `=======`, `>>>>>>>` в файле при конфликте?

`<<<<<<< HEAD` — начало варианта из текущей ветки. `=======` — разделитель между вариантами. `>>>>>>> имя_ветки` — конец варианта из сливаемой ветки.

4. Почему интерактивный rebase нельзя применять к публичным веткам?

Rebase переписывает историю: старые коммиты заменяются новыми с другими хешами. Если ветка уже опубликована и с ней работают другие люди, у них возникнут конфликты и рассинхронизация. Поэтому публичные ветки лучше не rebase-ить без крайней необходимости.

5. Зачем release-ветка мёржится и в `main`, и в `develop`? Что будет, если забыть слить в `develop`?

В main она попадает, чтобы выпустить релиз. В develop — чтобы изменения релиза (версия, changelog, мелкие исправления) не потерялись и вошли в следующую версию. Если забыть слить в develop, следующая разработка может откатить версию или потерять исправления.

6. Чем hotfix отличается от обычной feature-ветки? Почему hotfix ответвляется от `main`, а не от `develop`?

Feature — плановая новая функция, она идёт от develop. Hotfix — срочное исправление уже выпущенной версии, поэтому он идёт от main. Если ответвить hotfix от develop, можно случайно притащить в продакшен незавершённые функции из разработки.

7. Что такое аннотированный тег и чем он отличается от lightweight-тега?

Аннотированный тег — отдельный объект Git с сообщением, автором, датой и хешем. Lightweight-тег — просто указатель на коммит. Для релизов используют аннотированные теги, потому что они содержат метаданные и лучше подходят для истории версий.

8. Какие недостатки GitFlow вы заметили при выполнении работы? В каких случаях GitFlow будет неоптимальным выбором?

Много веток и слияний, сложнее для новичков, избыточен для проектов с непрерывным развёртыванием. Неоптимален для маленьких команд и веб-приложений с частыми релизами. Часто лучше Trunk-Based Development или GitHub Flow.
